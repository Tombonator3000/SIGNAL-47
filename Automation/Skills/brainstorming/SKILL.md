# Brainstorming into a usable design

Understand the intended outcome before building. Read current project decisions, relevant code and the conversation first. Reuse settled direction; a follow-up or a new skill invocation does not reset the user's authorization.

## Choose the useful depth

- **Assessment:** when the user asks whether an approach is useful, investigate and give a grounded recommendation. A small reversible feasibility probe can support the answer. Label its scope and limits; do not silently turn a comparison into a product migration.
- **Bounded change:** inspect the existing flow, state the intended change and meaningful checks briefly, then implement within the request. No mandatory spec, planning skill or fresh approval ceremony.
- **Architectural work:** compare credible approaches when a real choice remains, choose a justified provisional direction within the brief, and write a coherent design in the project's established location. Cover boundaries, data flow, errors, dependencies and observable acceptance criteria. If implementation is requested, continue through implementation and verification after this design work.

Hidden complexity calls for a revised plan and an explanation of the implications. It does not by itself revoke authorization or require ending the turn. Clarify only the decisions that cannot be resolved responsibly from the brief and existing context.

## Resolve uncertainty without a compulsory interview

Separate facts, existing decisions, reasonable assumptions and required user choices. Ask only when missing information materially changes the outcome and cannot be inferred. Ask early and continue independent work while an answer is pending. A required answer remains required; elapsed time is not consent.

An instruction to implement, fix or continue authorizes the ordinary reversible work necessary for that outcome. A request solely for ideas remains an ideas task. Approval for one project does not authorize actions in another. New spending, external communication, destructive changes or publication still need the authorization applicable to the actual action. Do not ask again for an action already covered by the conversation.

Use available visual tools when a diagram, mockup or comparison will make a real decision clearer. Follow their actual availability and authorization requirements; do not require a separate visual-companion offer before every reversible preview. A missing optional tool is not a reason to abandon text, code or other useful design work.

## Make the design implementable

State what the user or player does, what responds and the observable outcome. Keep units focused, interfaces understandable and ownership clear. Reuse existing patterns and preserve functioning behavior. Avoid unrelated refactors and speculative features.

For a large request, map every required deliverable and its dependencies before selecting the first increment. For each increment, retain a baseline, build, run appropriate checks, inspect the result and correct material defects. A completed increment is a checkpoint; continue with remaining authorized requirements. Do not substitute a plan or one polished example for the requested complete outcome.

Review a substantial design for contradictions, missing requirements, unclear assumptions and unnecessary scope. Resolve these before dependent implementation. Use an available planning skill only when useful; if none is installed, plan directly and use the project's normal implementation workflow. There is no required `writing-plans` dependency or exclusive terminal skill.

## Finish against the request

Before ending, compare the result with all requirements, including later corrections. Complete available implementation, relevant verification and authorized delivery. Stop optional polish once acceptance criteria pass, then move to the next required item. If an external dependency blocks part of the request, preserve evidence, complete independent work and identify the precise remaining dependency without calling the whole task complete.

Report the concrete result and material limits. Never imply that an assessment is an implemented feature, that a self-review is an independent test, or that work continues in the background without a running job.
